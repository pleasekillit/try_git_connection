# pyFastGithub 概要设计

## 1. 总体方案

采用**方案 A：本地 HTTP 代理 + HTTPS 中间人（用户态）**，不使用 WinDivert 内核驱动。

```
┌──────────┐  系统代理   ┌───────────────────────────────┐   纯净IP+定制SNI   ┌────────────┐
│ 浏览器    │ ─────────▶ │  pyFastGithub 本地代理         │ ────────────────▶ │ GitHub 上游 │
│ git/其它  │  127.0.0.1 │  ┌─────────┐  ┌─────────────┐  │                    │ (最快IP)    │
└──────────┘  :38457     │  │ CONNECT │→ │ TLS MITM    │  │                    └────────────┘
                         │  │  解析   │  │ 动态证书     │  │
                         │  └─────────┘  └─────────────┘  │
                         │        ▲              ▲        │
                         │   ┌────┴────┐   ┌─────┴──────┐ │
                         │   │DNS 解析  │   │IP 测速排序  │ │
                         │   │DoH/TCP  │   │            │ │
                         │   └─────────┘   └────────────┘ │
                         └───────────────────────────────┘
```

### 1.1 为什么不用 WinDivert（与原版的差异）

| 维度 | 原版（WinDivert） | 本方案（系统代理） |
|---|---|---|
| 工作层级 | 内核驱动抓包改包，DNS+端口劫持 | 用户态 HTTP 代理 |
| 权限 | 管理员 + 装驱动 | 仅装 CA 需管理员一次 |
| 透明度 | 全局透明，无需应用配置 | 需应用走系统代理；git 需显式配置 |
| 可移植性 | 仅 Windows | 逻辑可跨平台（系统代理实现按平台分支） |
| 复杂度 | 高 | 低 |

> 结论：以牺牲少量"透明性"换取实现简单、无驱动依赖、易维护。

## 2. 架构分层

```
scripts/
├── cli.py                 表现层：命令行入口、生命周期编排
├── config/                配置层：模型、域名匹配、JSONC 加载
├── resolver/              解析层：DNS 纯净解析、IP 测速、结果缓存
├── certs/                 证书层：CA 生成、域名证书签发、CA 安装
├── proxy/                 代理层：监听、CONNECT 分发、MITM、上游转发、HTTP 报文解析、流量统计
├── sysproxy/              系统层：Windows 系统代理设置与还原
└── utils/                 通用：日志
data/                      数据层：全局配置 + 域名规则（JSON）
```

分层依赖方向（自下而上）：`utils` → `config` → `resolver`/`certs` → `proxy` → `cli`。
`sysproxy` 独立于网络栈，仅被 `cli` 调用。

## 3. 模块划分与职责

| 模块 | 职责 | 关键类/函数 |
|---|---|---|

## 4. 关键流程

### 4.1 启动流程
1. 解析 CLI 参数 → 定位 `data/`。
2. `load_config` 装配 `AppConfig`。
3. `CertAuthority.ensure()` 确保 CA 存在；必要时安装。
4. 启动 `ProxyServer`（后台线程）。
5. 若非 `--no-system-proxy`，设置并记录原系统代理。
6. 主线程等待 Ctrl+C；收到信号后还原系统代理并退出。

### 4.2 HTTPS 请求（CONNECT + MITM）
1. 客户端 `CONNECT github.com:443`。
2. 命中规则 → 回 `200 Connection Established`。
3. 用 `github.com` 的服务器证书在客户端连接上做**服务端 TLS 握手**。
4. 读取明文 HTTP 请求（头 + 体，含 chunked）。
5. 若规则含 `response` → 直接回自定义响应并结束。
6. 否则 `Upstream` 解析最佳 IP，按 SNI 策略连接上游 TLS，转发请求、读响应。
7. 回写给客户端；按响应是否成帧决定是否保持连接。

### 4.3 未命中域名的 CONNECT
- 纯 TCP 隧道：正常解析目标主机并双向拷贝数据，不做 TLS 终结。

### 4.4 上游 SNI 策略
`DomainConfig.sni_pattern()` 决定 SNI 值：
- `tls_sni=false` → 空值 → 握手时不发送 SNI。
- 默认 → `@domain`（即发送真实域名）。
- 自定义 → 按 `@domain`/`@ipaddress`/`@random` 变量替换。

## 5. 数据设计（逻辑与数据分离）

- 全局参数：`data/appsettings.json`。
- 域名规则：`data/appsettings/appsettings.<group>.json`，按组拆分（github/google/packages…）。
- 运行时产物（非代码）：`cacert/`（CA 与域名证书）、`logs/`。
- 代码中**不硬编码**任何域名规则；新增站点只需加 JSON 文件。

## 6. 技术选型

| 需求 | 选型 | 理由 |
|---|---|---|
| TLS/证书 | `cryptography` | 事实标准，纯 Python 可用 |
| DNS | `dnspython` | 支持 DoH/TCP，成熟 |
| DoH 传输 | `httpx2`（dnspython 2.9 内部使用） | 随 `dnspython[doh]` 安装；dnspython 2.9 起 DoH 依赖由 `httpx` 改为 `httpx2` |
| 并发测速/多连接 | `socketserver.ThreadingTCPServer` + 线程池 | 阻塞模型简单、易测、易排错 |
| 测试 | `pytest` | 自测框架 |

### 6.1 为何采用阻塞 + 线程而非 asyncio
- MITM 需要在已建立的连接上"升级为 TLS"，asyncio 的 `start_tls` 在流式场景较易出错。
- 该工具为个人本机使用，连接数不高，线程模型足够且更易维护与调试。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 部分应用不读系统代理（如未配置的 git） | 文档提示 `git config --global http.proxy`；后续可加 PAC |
| MITM 证书未受信导致报错 | 提供 `install-ca`，并在启动时检测/提示 |
| 上游证书名不匹配 | 规则支持 `tls_ignore_name_mismatch` |
| DoH 被阻断 | 多 DoH + TCP DNS 兜底，均可在配置中改 |
| HTTP/2 站点 | MITM 不协商 h2，客户端回退 HTTP/1.1 |
| 退出未还原系统代理 | `try/finally` + 信号处理保证还原；另存还原快照 |
